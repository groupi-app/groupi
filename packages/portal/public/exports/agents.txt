<a id="tasks"></a>
Choose one integration task
Canonical passage: http://localhost:4173/v2/agents#tasks

First own-account Event: needs a legacy collection key and authority to create. Private Event widget: needs an existing readable Event and a private local rendering context. Group Events: needs legacy credentials and current eligible Group read authority; audience changes are a separate optional task. Event updates: needs events.update or legacy events-write and the current Event role. Connect another user: needs an eligible registered client, configured issuer, exact callback and explicit user consent. Follow only the task needed, then the exact API reference.

<a id="identity"></a>
Select instance, account and credential mode
Canonical passage: http://localhost:4173/v2/agents#identity

Establish the intended API origin, matching website, account, requested operation and existing user authorization before requests. Legacy own-account creation verifies GET /profile and personId. Bounded Event reads/updates require explicit actions and resource selection intersected with current authority; not all bounded keys have identity access. For delegated tokens, global /profile is denied: validate exact issuer/audience, state, PKCE S256 and nonce; use permitted signed OIDC claims/userinfo. openid alone gives an opaque app-and-instance-specific subject. A bounded key or delegated token cannot create an Event. Stop if the capability or authority is missing; never substitute an owner key.

<a id="execution"></a>
Simulation, preparation and real execution
Canonical passage: http://localhost:4173/v2/agents#execution

Documentation access is not account authorization. Run in the portal changes fixtures only and accepts no key. Copy local examples for real work; keep credentials in the user’s local environment or secret manager, never prompts, URLs, browser bundles or logs. An agent must establish authorization separately before live writes, invitations, audience changes, app registration or publication. Do not install an assumed SDK package: registry availability is unverified; use the direct HTTP examples with their stated runtimes. Report a prepared integration, a simulation and verified real success distinctly.

<a id="recovery"></a>
Recovery and privacy
Canonical passage: http://localhost:4173/v2/agents#recovery

For POST /events retain the exact payload and <unix-ms>.<uuid-v4> Idempotency-Key before sending. On uncertain response replay unchanged within 24 hours; conflict, expiry or changed account/instance means inspect, not a blind new create. Other writes require operation-specific inspection rather than assuming this guarantee. 401/403 remain failures. An Event read grant is not permission to republish; the first widget is private/local. No automatic invitations, cleanup, audience changes or background consent.

<a id="completion"></a>
Check completion against the task
Canonical passage: http://localhost:4173/v2/agents#completion

First Event: one undated Event, matching permitted read-back and correct website /event/{id} link, retained replay identity, no invitations. Widget: private local display of permitted data with loading, empty, success and error states; no realtime promise. Group recipe: permitted upcoming/undated previews or empty success, correct pagination and no audience mutation; sharing is a separate authorized task. Update: permitted read-back matches the requested fields, or explicitly report that read permission is missing. Delegation: validated identity and permitted selected-resource operation; disconnect denial verified only when authorized. Record the actual environment and evidence; source availability is not deployed acceptance.
