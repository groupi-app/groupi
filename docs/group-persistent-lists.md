# Persistent community lists

Community lists are persistent Group tools, independent of private Invite Lists and Event Bring Lists. They never convert into Event commitments, affect RSVP, inherit into Events, or send publication/contribution notifications.

An Owner controls LIST availability and creation policy. Managers create by default; the Owner may allow current eligible members to create. Current eligible managers may list, read configuration, configure and delete preserved lists while LIST interaction is disabled. Ordinary reads, contributions and results remain disabled. Required joining-questionnaire completion gates current content for managers too. Owner policy recovery and retained own contributions are narrow exceptions.

Each instance has a title (trimmed 1–100 characters), optional description (at most 2000 characters), and immutable disclosed visibility. MEMBERS shares current entries with eligible members; MANAGERS reveals an author's entries to that author and eligible managers only. Account deletion purges private entries and retry records; shared latest entries survive anonymously. Creator and last editor references are anonymized. Group retirement deletes all list configuration, entries and retry state immediately, alongside ordinary forms.

Eligible members add, edit, mark complete and remove their own text entries (trimmed 1–2000 characters). Eligible managers edit or remove any entry, including anonymous shared entries. There are no quantities, assignees, claims or Event obligations. An entry starts at revision 1; changed text/completion increments its revision. Configuration title/description changes increment the list version without resetting entries. The original title snapshot remains available in the author's own recovery view, which never fetches later private definitions. Own retained entries may be read or removed after membership loss, ban, disabled interaction or incomplete onboarding; editing requires current interaction eligibility.

Add requires the current list version and a timestamp.UUID request ID issued within the retained 24-hour window. The normalized text and supplied version define its exact body. Concurrent/repeated identical requests create one entry; changed bodies conflict. Recovery rechecks current authorization and availability, reports PRESENT or REMOVED, and never recreates an entry removed since success. A previously successful request can recover after configuration changes; a new stale-version request conflicts. Request expiry is scheduled transactionally with creation. External delivery is never scheduled.

Edit requires the current list version and expected entry revision. A repeat of the current text/completion is an idempotent recovery; a stale changed edit conflicts. Removal requires the expected entry revision; stale removal conflicts and a missing entry is an idempotent success through the authenticated mutation. REST returns not-found for a missing scoped entry. Managers must still have current enabled interaction eligibility to remove another author's entry. Settings deletion remains available to eligible managers while disabled.

Web and native expose direct hub, creation, settings, entry use and own recovery routes, including reusable title/description templates. Before submission they explain visibility and account deletion behavior. An uncertain add preserves its exact body, version and request ID for retry. Settings creation/configuration has no automatic retry; inspect the saved list before repeating an uncertain creation. CLI exposes the same scoped operations, explicit visibility, expected versions/revisions, confirmed deletion and request IDs. DELETE entry bodies are opt-in in CLI transport.

Validation covers real authenticated Convex/session and scoped HTTP operations, three account deletion paths, mounted consuming SDK/provider web/native controls, and CLI through a local HTTP listener. Provider fixtures model local server responses; they do not prove device, live provider or screen-reader behavior.
